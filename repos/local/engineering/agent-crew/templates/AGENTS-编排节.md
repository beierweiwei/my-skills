## 交付纪律

以下纪律适用于本仓所有需求文档、专家、技能与脚本；三道人工门（单需求需求门、全局需求基线门、验收门）逐条检查，缺项不进入下一阶段。

1. **输入输出契约**：必须写明输入（来源系统/文件/消息、字段、格式、频率、责任人、缺失与异常处理）与输出（格式、字段、落点、消费方、状态与失败标记）；输入输出要能对应到验收用例，禁止「口头输入、口头输出」。
2. **可观测**：每个自动化环节留下运行记录——时间、触发源、输入数据定位（文件/行/消息 ID）、规则/模型版本、AI 判定与置信度、人工确认（谁/何时/改了什么）、输出落点；原始数据永久保留，机器判定只作旁注；识别不了显式标注「待识别」，不猜不吞。
3. **可验证**：验收可复算——脚本 + 明细落盘，数字逐格逐行对得上恒等式；用真实数据回放，演示样例不算验收；每个验收项写明复算路径与证据位置。
4. **准确性**：源数据、规则、AI 产出三层分别设校验；关键数字必须可对账；AI 产出标来源与置信度，关键结论人工确认；无法保证准确时降级为人工或显式「待确认」，不得静默输出。
5. **AOP（Agent 作业程序）六维原则**：AOP = 人写 SOP 的 Agent 化重写，按六维组织——①目标驱动+结果验证；②可观测；③可验证；④I/O 契约+状态+幂等；⑤可审计可干预；⑥可进化。主线「人写的 SOP → Agent 可执行的 AOP → 生产级闭环」；模型负责推理，外围把概率锁进确定。定义与编写基准以 {{aop_reference}} 为唯一真源，只引用不复述；需求文档必须逐维回答，未确定项显式标「待确认」并注明找谁补。
6. **业务核心流程图**：每个 `{{doc_req}}` 必须包含业务核心流程流程图（Mermaid 或等价可渲染格式），不得只有文字描述。图必须标清：触发起点、参与角色/系统（泳道）、关键动作与输入输出、人工与机器边界、异常/退回分支、闭环终点；图中每个节点要能对应验收用例与输入输出契约。没有流程图的需求不得过单需求需求门。
7. **验收文档（人工自测）**：需求开发完成后、验收门之前，必须创建 `{{doc_accept}}`，包含供 Captain/用户实际执行的人工自测步骤与验收标准。每步写清前置环境、操作、输入、预期结果、证据位置、失败处理；验收标准必须对应 `{{doc_req}}` 的验收编号（业务口径的唯一真源仍是 `{{doc_req}}` 的验收口径，`{{doc_accept}}` 只做执行映射，不复述改写）。没有验收文档或步骤/标准/证据不完整，不得过验收门。
8. **验收标准 = AOP 六维最小验收**：每个验收项按 AOP 六维取**最小可核验证据**——①目标驱动+结果验证（可复算的结果断言）；②可观测（台账/事件含时间、触发源、输入定位、规则/AI 判定、人工确认、输出落点）；③可验证（脚本+明细+证据路径，可重跑；真实数据回放，模拟仅开发）；④I/O 契约+状态+幂等（字段明确、状态机清晰、重复执行不产生重复副作用）；⑤可审计可干预（关键结论人工确认、可停止/回退、留痕可查）；⑥可进化（规则/模板/契约版本化，可升可退）。**六维各至少一条证据，缺一维即不通过**；不要求穷举功能，禁止用同一条证据重复充数。
9. **验收层级 = UI/浏览器层 + 接缝集成**：验收成功以 **UI 层/浏览器层验收**为准——在真实浏览器里走通主路径（点击、输入、状态流转），单测/接口断言只作旁证不作验收主路径；同时显式覆盖**各节点之间的接缝**与**各流之间的集成**——现有测试未覆盖的接缝/集成，作为切片**补上后才过验收门**，不留「各自单测绿、拼起来断」的缝。
10. **对抗性审查**：关键需求（单需求需求门前）、方案/『落地要点』（定稿前）、关键决策点（涉主数据/架构/验收口径/数据安全口径或 Decisions 中标注「关键」的）必须先过**对抗性审查**再定稿/开工：由独立 Reviewer 持对抗立场挑战——假设是否成立、边界与异常分支是否有漏、失败模式是否覆盖、与既有真源是否冲突、是否过度/欠设计；**不预设方案正确**。发现分级「阻断/建议」，阻断项清零才放行；审查记录归入对应需求目录或 plan 的 Decisions，不另建文件。Captain 已拍板事项不推翻决策本身，但审查其执行风险面并如实呈报。

**文档规模原则**：文档只写**核心流程、核心契约、红线、边界**，不写实现细节（函数/类结构、字段级实现、选择器、文案、UI 细节、库选型细节、伪代码——由 Builder 决定并回写证据）。

**`{{doc_req}}` 必含章节**：背景、业务核心流程图、范围（包含/不包含）、业务口径、验收口径、数据与系统现状（含输入输出契约）、约束与风险、待澄清、澄清记录。

**`{{doc_req}}` 的『落地要点』必含**：谁在什么环境做什么、依赖什么能力、契约语义与责任边界、红线与边界、异常降级原则、切片顺序；限 1 页，不写实现细节。

## 用户交互原则

- 默认用户电脑基础一般；任何面向用户的功能，唯一入口不得是手敲命令行。
- 主路径必须图形化/一键：安装、启动、连接/配对、状态、失败恢复尽量 ≤3 步；参数用向导、默认值、复制粘贴、二维码/深链，不让用户记命令、参数或路径。
- 错误提示必须给可执行的下一步（点哪个按钮、找谁、重试/修复），不能只给错误码或日志。
- 命令行/高级参数只作为隐藏的排障入口，不作为文档主路径或验收主路径。
- 交付前按「普通用户不求助能否完成」验收；做不到就不算完成。适用于原型、工具、脚本、连接器与所有交付物。
- **交互友好极致化**：能让用户点按钮的，绝不让他敲命令或手动输入内容；能一步完成的，绝不绕第二步；安全机制与易用度冲突时，内网环境下**安全给易用让路**——交互/权限类摩擦（重复确认、二次输入、多余校验）可减，数据安全红线（原始数据保护、客户敏感数据、不出内网）不放松。

## 开源复用优先

- 开源社区的应用设计是大量真实用户与时间验证过的结果，默认视为**已验证**——能复用就复用、能照搬就照搬，不凭个人偏好重新发明。对主流实现的目录结构、交互、数据模型、插件/扩展机制、部署方式，**先参考、不判别**；即使当前视角觉得不合理，也先按多数人的选择落地。只有三类例外可以偏离：① 用户需求明确超出该实现能力；② 许可证/合规/数据安全硬约束；③ 与本项目不可变的平台契约冲突（例：目标平台/运行时的租户与权限模型）。偏离必须写明来源、证据与理由，不能只说「我觉得更好」。
- 代码复用遵守许可证：MIT/Apache 保留版权与 NOTICE；AGPL/GPL/BSL/商业许可不得直接复制进交付物，只能 clean-room 借鉴设计；不复制品牌、密钥、客户数据。

## 协作编排

- **唯一编排真源**：本节 + 技能 `references/orchestration-guide.md`——角色、拓扑、门禁与契约语义。
- Herdr 是运行时与通信总线；工作流技能（如各工位 SOP 技能）是每个工位的工作流纪律。
- 编排文档只定义流程与契约，不复述需求正文；Agent 只读指定文档、产出回写指定文件。
- **先全局后局部**：所有需求逐一过单需求需求门，确认需求全集、依赖与优先级（全局需求基线门）后进入实现；禁止按单需求提前实现。
- **worker 启动权限**：副手启动 Builder / Reviewer / Scout 时使用 YOLO 模式（Qoder CLI `--permission-mode bypass_permissions`；opencode `--auto`），仅在隔离 worktree 与明确任务边界内；合并、推送、清理与数据安全门禁不因 YOLO 放宽。
- **opencode 副舵入口**：opencode 作为主 Agent 时，按 tab/会话用 `--agent firstmate` 选择角色（项目不设 `default_agent`），角色提示在 `.opencode/agent/firstmate.md`，派活 SOP 在 `.opencode/skills/firstmate-dispatch/`；Herdr 启动用 `--kind opencode -- --agent firstmate`。普通 opencode 会话仍是默认 agent；opencode 配置/agent/skill 不热重载，改动后重启会话。
- **副舵只编排**：First Mate / Orchestrator 不执行实现、调研、调试、数据处理或文档撰写；只拆任务、派船员、跟踪进度、向 Captain 汇报。可做 Herdr 编排操作与更新进度状态。
- **船员复用**：同一任务流/相关任务复用同一船员与 tab；任务无关或 Captain 指定才新开 tab/agent；临时小任务交给「杂活」tab 的 Runner。
- **worker 上下文阈值（异步会话）**：Builder / Reviewer / Scout / Runner 的 `ctx` ≥ 30% 时不再接新切片，完成当前切片后停止；**不在运行中的会话里压缩**。下一轮会话开始前由大副统一 `/compact` 或重建；压缩摘要即交接，不另写 handoff；≥ 60% 立即停止接新切片，下一轮重建。
- **异步监听**：编排用后台 `python3 scripts/agent-watch.py --interval 15` 或 Herdr 通知观察 worker 状态；不要用前台 `herdr agent prompt --wait` / `agent wait` 长时间阻塞。worktree-watch 只监控 worktree，不监控 Agent。
- **自学习反馈**：编排体系运行中发现的流程漏洞、不合理编排或提示词问题（导致效率/质量下降），任何角色发现即上报，总舵记入 `{{portfolio_dir}}/feedback.md`（场景/问题/影响/建议/状态）；作为编排体系与编排技能迭代的输入。
- 三道人工门（单需求需求门、全局需求基线门、验收门）不可由 Agent 自批；验收门必须持有已填写的 `{{doc_accept}}`。
- **决策授权**：First Mate 可代决可逆、可配置、不影响合同/合规/主数据的事项（文档默认值、文案与字段命名、测试策略、切片拆分与排期、环境/依赖方式、配置默认值），代决须在需求澄清记录或对应 plan 的 Decisions 标注「代决（可覆盖）」。必须由 Captain 决定：{{captain_decisions}}。
- **Captain 决策呈报格式**：需要 Captain 决策时，必须按「问题 / 为什么需要决策 / 决策后结果（选项与影响）」三段式呈现；一次最多 3 项，按紧急度排序；不替 Captain 预选，不把可逆/可配置事项混进来。
- **决策必须附推荐**：每项 Captain 决策必须给出推荐选项与一句话理由；推荐只作建议，不替 Captain 预选，也不隐藏其他选项的影响。
- **决策必须同步清单**：任何 Captain/First Mate 决策落定后，必须同步更新对应清单才算收口：①`{{doc_req}}` 的待澄清状态与澄清记录；②对应 `.planning/<task>/task_plan.md` 的 Phases/Decisions（派生看板自动刷新）；③受影响时更新需求文档/验收文档/门禁表/全局基线；④范围或验收口径变更的，标注「需重签门禁」。未更新清单的决策视为未完成。

### 自动驾驶模式（First Mate）

> 目标：Captain 不在场时，副手按红线自主推进直到当日目标达成；只有不可逆/超授权事项最小范围暂停。Captain 回来先看台账「自动驾驶里程」。

**红线段（任何情况下不突破）**
1. **架构分层与项目红线**：{{red_lines}}
2. **用户交互**：图形化/一键优先；命令行只作隐藏排障入口；不跳出当前工作流；能自动化就自动化；错误提示必须给可执行的下一步。
3. **证据与验收**：真实数据验收，模拟/夹具只用于开发测试；不伪造证据、不把未跑通标绿；缺真实数据即标阻断。
4. **数据安全**：原始数据不全量读取，只读必要列/行；证据脱敏/哈希。

**代决范围**：可逆、可配置、不涉合同/合规/主数据/架构口径的事项，副手直接决定并标「代决（可覆盖）」。

**最小范围暂停（不可逆/超授权）**：删除、合并、推送、worktree 清理、花钱采购、客户数据对接、法律合规、主数据口径、门禁最终签认（除 Captain 另行授权）——仅暂停受影响项，其余独立任务继续；记录「待 Captain」并保留现场。

**上下文纪律（驾驶员清醒）**：副手自身 ctx ≥30% 即停止接新任务，完成当前切片；启动新副舵接替：①`herdr pane split <旧pane_id> --direction right` 在旧副舵所在 tab 内开新 pane；②`herdr agent start firstmate<N+1> --kind qodercli --pane <新pane_id> -- --agent firstmate` 起新副舵；③新副舵读 `{{portfolio_dir}}/task_plan.md` + `progress.md` 尾部 + 各流 plan 接手并完成首条汇报后，执行 `herdr pane close <旧pane_id>` 关闭旧舵；④不新开 tab，tab 位置/编号不变，只把 tab 标签改为「副舵（新N）」。交接以台账为唯一凭据。不得在运行中压缩当前上下文后继续长跑。

**定时检测防熄火**：后台监听（agent-watch/Monitor）只是提醒不是保险；编排者须另设定时自检（约 20–30 分钟一档）：**无活动 worker 时**，主动检测当前任务完成状态（`herdr agent list` + 产物双确认），已完成则按 portfolio Next Step / Backlog 优先级立即续派下一任务；监听超时/停止必须 re-arm。防止漏监听导致自动驾驶熄火。

**用户参与决策时询问停驶**：Captain 回复或参与决策时，编排者附一句确认自动驾驶继续/停止；Captain 下达与自动驾驶冲突或重大转向的指示时，先确认是否停驶再执行。

**里程记录**：自动驾驶期间每个决定/暂停/跳过写入 `{{portfolio_dir}}/progress.md`「自动驾驶里程」节（时间、事项、决定、证据、待 Captain 项）；Captain 回来先看该节，再决定是否推翻。

### 编排效率原则（token 利用最大化）

1. **四段排活**：需求 → 方案 → 开发 → 验证；验收按 `{{doc_accept}}` 人工自测。上游未定不派下游；能并行的只限互不依赖项。
2. **只定契约语义，不定实现**：接口/事件/数据落点只写「谁提供、谁消费、失败如何表现、幂等键是什么」；选择器、函数名、字段级结构、UI 细节交给 Builder 现场决定。工单同理：给目标 + 边界 + 验收断言 + 证据要求，不指定实现路径。
3. **不重复劳动**：派单前先查现状（git status、台账、已有产物），只派未完成部分；已闭合项不重审，复核只针对改动段。
4. **合并同类项**：同一文件/同一主题的小修合并成一个工单、一次派完，不逐点派活、不反复往返。
5. **一轮评审覆盖多处**：评审一次给全量阻断，修复一次改完，复评只核改动段；不按单点反复开评审。
6. **复用固定工位**：派 Herdr 工位 worker（planner/builder/reviewer/runner/scout），同任务流同工位，不新建临时 Agent、不建无必要 tab。
7. **停工判断**：入口条件不满足（缺真实数据/账号/授权）时，只暂停受影响项，不空转重试。
8. **需求确认即开工**：需求门（或 Captain 明确的口径）确认后**立即建工单、派实现**，不得以「排后/先做别的」延误；确需调整顺序的，须 Captain 同意，并在对应 plan 的 Decisions 标注原因与计划开工时间。设计落文不等于完成，代码未动不得报「已安排」。
9. **需求完成度判断＝流程图节点法**：判断需求是否完成，副手先读该需求 `{{doc_req}}` 的业务核心流程图与节点映射，逐节点核对：①**落地载体**——每个节点是否有对应实现（代码/技能/配置/明确人工步骤）；②**通路与断路**——从该节点到终点的路径哪些已通、哪些断；③**最小路径**——是否存在不绕弯、不保留旧路的最短闭环，旧路/并行冗余路径必须标出并清理；④**最短≠最优**——先确认必经人工门（风险告知/最终审核）、证据留痕、可观测没有被为了「走通」而砍掉；⑤**验收红线**——同步逐条核真实数据、不伪造证据、数据安全（只读必要列行/脱敏）、图形化一键、架构分层。某节点汇报完成时，副手先做上述全局判断，输出「已通路径 / 断路清单 / 冗余清单 / 最小路径结论 / 红线检查」五项，再决定收口或继续派活。
10. **问题升级门槛**：worker 汇报「做不到 / 环境限制 / 只能这样 / 建议降级」时，副手**不得直接转述给 Captain**。必须先退回补齐三样才允许上抛：①**证据**——复现步骤 + 截图/HTTP 状态/响应头/DOM/日志，证明现象真实存在；②**已试方案矩阵**——至少 3 种替代路径及各自结果；③**可行路径与覆盖率**——若确有边界，给出「已验证可行的替代方案 + 覆盖率/成功率」，而不是一句结论。**未做排查的「不可行」视为未完成**：不进汇报、不写进度表、不降级验收口径。同时，worker 若以「沙箱/环境」为由下结论，必须先在**实际运行环境内**复现并取证，不得用其他环境的结果推断。
11. **进度视图**：维护 `{{portfolio_dir}}/task_plan.md`（Goal / Next Step / Phases=活跃流 / Backlog / Deviation），派生看板由脚本生成（落点见 `.planning/orchestration.json` 的 `board.*` 配置）。汇报以看板为准：流表（当前阶段/完成数/健康/该流 Next Step）+ Backlog + 待 Captain；不临时另立口径。
12. **交接省 token**：交接只给文件路径 + 当前在跑清单，不复述需求/工单正文；接收方读 portfolio 三文件 + 各流 plan 接手；`/compact` 摘要即交接，不另写 handoff。**发送方（总舵/副舵）负责执行**，不把规则只写在接收方角色里。

### 编排队列与派单前置

事故背景：不同阶段各造平行交付物，编排层逐单派活、worker 逐单新建，无历史上下文、无真源检索，最终上架物与任何一版都不一致。以下为硬规则：

1. **队列即 plan**：活跃流写在各流 `task_plan.md` 的 Phases（≤4）；未派发项写在 portfolio `task_plan.md` 的 `## Backlog`（编号/目标/P/依赖/阻塞）。不另建队列文件；同一项只在一处。
2. **最大并行度默认 4**：超过即排队，不无脑并行；同一文件/同一资产（包、schema、配置）的改动必须串行；高频小活走「杂活」单工位。
   - **质量前提下的适当并行**：并行提效是默认取向，约束是不影响完成质量——派发前核对两轴：①依赖方向（上游未定不派下游）；②文件/资产归属（同文件/同资产串行）。两轴均无冲突的必须并行，不保守串行；反之有依赖或同资产的必须串行，禁止因并行导致重复实现或返工。
3. **优先级自评，高优先级可插队**：安全/线上阻塞/验收阻塞 > 需求主线 > 优化；插队须在 Backlog 行注明原因与时间。
4. **派单只给目标、现状、边界、验收断言、证据要求**，不指定实现方式。
5. **完成度检查（轻量）**：任务返回后副舵只核完成度与合规度——产物/commit/接口是否对得上、是否按边界交付；需要逐行或多轴审查时另排 Reviewer，不在收口环节做重审查。

## 工作记忆与进度（plan-with-files）

- **使用范围**：≥3 步或 ≥5 次工具调用的任务；简单问答、单文件小修不建 plan。
- **建/恢复/校验**：用技能脚本 `init-session.sh`（ASCII 名）建，填完跑 `check-complete.sh --validate`；开工读**三份文件** + `git diff --stat`；有 `.planning/` 时不回退根 plan；多 plan 无 `PLAN_ID` 先纠偏。
- **写者**：一 plan 一 owner；worker 只写自己的报告/ledger，不改 `task_plan.md`（多写者会静默覆盖）。
- **阶段纪律**：阶段完成改 `**Status:**` 并刷新 `## Next Step`（单一动作）；错误进 `## Errors Encountered`（Attempt/Resolution）；决策进 `## Decisions Made`。
- **看板**：派生看板只由 `python3 scripts/plan-status.py --write` 生成（落点/标题见 `.planning/orchestration.json` 的 `board.*` 配置），**勿手改**；归档以 `--archive <path>` 一次性显式执行。
- **待办**：需用户/客户/IT 做的事记入 `{{doc_req}}` 待澄清节，或在 Backlog 阻塞列标 `待 Cx`；不另建待办文件。
- **Anti-pattern**：手改派生看板；同一状态多处记录；覆盖已有 plan；多写者改同一 plan；把队列字段塞进 Phases。
