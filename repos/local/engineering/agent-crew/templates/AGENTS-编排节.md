## 交付纪律

以下纪律适用于本仓所有需求文档、专家、技能与脚本；三道人工门（单需求需求门、全局需求基线门、验收门）逐条检查，缺项不进入下一阶段。

1. **输入输出契约**：必须写明输入（来源系统/文件/消息、字段、格式、频率、责任人、缺失与异常处理）与输出（格式、字段、落点、消费方、状态与失败标记）；输入输出要能对应到验收用例，禁止「口头输入、口头输出」。
2. **可观测**：每个自动化环节留下运行记录——时间、触发源、输入数据定位（文件/行/消息 ID）、规则/模型版本、AI 判定与置信度、人工确认（谁/何时/改了什么）、输出落点；原始数据永久保留，机器判定只作旁注；识别不了显式标注「待识别」，不猜不吞。
3. **可验证**：验收可复算——脚本 + 明细落盘，数字逐格逐行对得上恒等式；用真实数据回放，演示样例不算验收；每个验收项写明复算路径与证据位置。
4. **准确性**：源数据、规则、AI 产出三层分别设校验；关键数字必须可对账；AI 产出标来源与置信度，关键结论人工确认；无法保证准确时降级为人工或显式「待确认」，不得静默输出。
5. **AOP（Agent 作业程序）六维原则**：AOP = 人写 SOP 的 Agent 化重写，按六维组织——①目标驱动+结果验证；②可观测；③可验证；④I/O 契约+状态+幂等；⑤可审计可干预；⑥可进化。主线「人写的 SOP → Agent 可执行的 AOP → 生产级闭环」；模型负责推理，外围把概率锁进确定。定义与编写基准以 {{aop_reference}} 为唯一真源，只引用不复述；需求文档必须逐维回答，未确定项显式标「待确认」并注明找谁补。
6. **业务核心流程图**：每个 `{{doc_req}}` 必须包含业务核心流程流程图（Mermaid 或等价可渲染格式），不得只有文字描述。图必须标清：触发起点、参与角色/系统（泳道）、关键动作与输入输出、人工与机器边界、异常/退回分支、闭环终点；图中每个节点要能对应验收用例与输入输出契约。没有流程图的需求不得过单需求需求门。
7. **验收文档（人工自测）**：需求开发完成后、验收门之前，必须创建 `{{doc_accept}}`，包含供 Captain/用户实际执行的人工自测步骤与验收标准。每步写清前置环境、操作、输入、预期结果、证据位置、失败处理；验收标准必须对应 `{{doc_req}}` 的验收编号（业务口径的唯一真源仍是 `{{doc_req}}` 的验收口径，`{{doc_accept}}` 只做执行映射，不复述改写）。没有验收文档或步骤/标准/证据不完整，不得过验收门。
8. **验收标准 = AOP 六维最小验收**：每个验收项按 AOP 六维取**最小可核验证据**——①目标驱动+结果验证（可复算的结果断言）；②可观测（台账/事件含时间、触发源、输入定位、规则/AI 判定、人工确认、输出落点）；③可验证（脚本+明细+证据路径，可重跑；真实数据回放，模拟仅开发）；④I/O 契约+状态+幂等（字段明确、状态机清晰、重复执行不产生重复副作用）；⑤可审计可干预（关键结论人工确认、可停止/回退、留痕可查）；⑥可进化（规则/模板/契约版本化，可升可退）。**六维各至少一条证据，缺一维即不通过**；不要求穷举功能，禁止用同一条证据重复充数。
9. **验收层级 = UI/浏览器层 + 接缝集成**：验收成功以 **UI 层/浏览器层验收**为准——在真实浏览器里走通主路径（点击、输入、状态流转），单测/接口断言只作旁证不作验收主路径；同时显式覆盖**各节点之间的接缝**与**各流之间的集成**——现有测试未覆盖的接缝/集成，作为切片**补上后才过验收门**，不留「各自单测绿、拼起来断」的缝。
10. **对抗性审查**：关键需求（单需求需求门前）、方案/『落地要点』（定稿前）、关键决策点（涉主数据/架构/验收口径/数据安全口径或 Decisions 中标注「关键」的）必须先过**对抗性审查**再定稿/开工：由独立 Reviewer 持对抗立场挑战——假设是否成立、边界与异常分支是否有漏、失败模式是否覆盖、与既有真源是否冲突、是否过度/欠设计；**不预设方案正确**。发现分级「阻断/建议」，阻断项清零才放行；审查记录归入对应需求目录或 plan 的 Decisions，不另建文件。Captain 已拍板事项不推翻决策本身，但审查其执行风险面并如实呈报。

**文档规模原则**：文档只写**核心流程、核心契约、红线、边界**，不写实现细节（函数/类结构、字段级实现、选择器、文案、UI 细节、库选型细节、伪代码——由 Builder 决定并回写证据）。

**`{{doc_req}}` 必含章节**：背景、业务核心流程图、范围（包含/不包含）、业务口径、验收口径、数据与系统现状（含输入输出契约）、约束与风险、待澄清、澄清记录。

**`{{doc_req}}` 的『落地要点』必含**：谁在什么环境做什么、依赖什么能力、契约语义与责任边界、红线与边界、异常降级原则、切片顺序；限 1 页，不写实现细节。

## 用户交互原则

- 默认用户电脑基础一般；任何面向用户的功能，唯一入口不得是手敲命令行。
- 主路径必须图形化/一键：安装、启动、连接/配对、状态、失败恢复尽量 ≤3 步；参数用向导、默认值、复制粘贴、二维码/深链，不让用户记命令、参数或路径。
- 错误提示必须给可执行的下一步（点哪个按钮、找谁、重试/修复），不能只给错误码或日志。
- 命令行/高级参数只作为隐藏的排障入口，不作为文档主路径或验收主路径。
- 交付前按「普通用户不求助能否完成」验收；做不到就不算完成。适用于原型、工具、脚本、连接器与所有交付物。
- **交互友好极致化**：能让用户点按钮的，绝不让他敲命令或手动输入内容；能一步完成的，绝不绕第二步；安全机制与易用度冲突时，内网环境下**安全给易用让路**——交互/权限类摩擦（重复确认、二次输入、多余校验）可减，数据安全红线（原始数据保护、客户敏感数据、不出内网）不放松。

## 开源复用优先

- 开源社区的应用设计是大量真实用户与时间验证过的结果，默认视为**已验证**——能复用就复用、能照搬就照搬，不凭个人偏好重新发明。对主流实现的目录结构、交互、数据模型、插件/扩展机制、部署方式，**先参考、不判别**；即使当前视角觉得不合理，也先按多数人的选择落地。只有三类例外可以偏离：① 用户需求明确超出该实现能力；② 许可证/合规/数据安全硬约束；③ 与本项目不可变的平台契约冲突（例：目标平台/运行时的租户与权限模型）。偏离必须写明来源、证据与理由，不能只说「我觉得更好」。
- 代码复用遵守许可证：MIT/Apache 保留版权与 NOTICE；AGPL/GPL/BSL/商业许可不得直接复制进交付物，只能 clean-room 借鉴设计；不复制品牌、密钥、客户数据。

- **汇报规则**：总结先行；细节锚定业务链节点；报下游（正向解锁）、上游（反向回改/解阻）、横向（其他流）影响；说人话，不用内部编号/agent 术语/工具名/commit hash/日志；需要溯源时最后一行「证据：」+ 一个入口或路径；细则见技能 `{{crew_acceptance}}` A5。
- **队列与排活**：活跃流写各流 `task_plan.md` 的 Phases（≤4）；未派发项只进 portfolio Backlog，不另建队列文件；默认最大并行 4，同文件/同资产串行；安全/线上/验收阻塞优先；派单前查现状、只派未完成，同类合并、一轮评审覆盖；需求确认即建单派实现。
- **完成度判断**：按需求业务链流程图逐节点核对落地载体、通路断路、冗余与最小路径、验收红线；节点完成先做全局判断再收口。
- **问题升级门槛**：worker 报「做不到/环境限制」先退回补证据、已试方案矩阵、可行路径与覆盖率；未排查的「不可行」视为未完成。
- **上下文纪律**：worker ctx ≥30% 停止接新切片，≥60% 立即停；运行中不压缩；交接 digest ≤30 行，只给路径 + 在跑清单。
- **三道人工门**：单需求需求门、全局需求基线门、验收门不可由 Agent 自批；先过全局需求基线门再进入实现，禁止按单需求提前实现；验收门必须持有 `{{doc_accept}}`，按技能 `{{crew_acceptance}}` A1–A5 抽验与呈报。

## 工作记忆与进度（plan-with-files）

- **使用范围**：≥3 步或 ≥5 次工具调用的任务；简单问答、单文件小修不建 plan。
- **三文件**：`task_plan.md`（真源）、`findings.md`、`progress.md`；一 plan 一 owner，worker 只写自己的报告/ledger，不改他人 plan。
- **阶段纪律**：阶段完成改 `**Status:**` 并刷新 `## Next Step`；错误进 `## Errors Encountered`，决策进 `## Decisions Made`。
- **看板**：派生看板只由脚本生成，勿手改；Current Phase 由脚本自动推导。
- **待办**：需用户/客户/IT 做的事记入 `{{doc_req}}` 待澄清节，或在 Backlog 阻塞列标 `待 Cx`；不另建待办文件。

## 技能版本与反馈

- **版本化**：SKILL.md 记版本，CHANGELOG 记变更；init 写版本戳，可对比安装版与源版。
- **update 感知**：安装版与源版不一致时提示重跑更新；失败项汇总并支持重跑，不静默跳过。
- **反馈回流门**：运行中发现的流程/提示词问题记入 `{{portfolio_dir}}/feedback.md`（场景/问题/影响/建议/状态）；发布时逐条销项（目标文件/版本/测试），建 `BACKLOG.md`。
