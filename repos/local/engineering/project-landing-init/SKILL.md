# 项目落地初始化

把空目录（或只有 `AGENTS.md` 的目录）变成可直接开工的客户智能体落地仓库。目标不是目录齐全，而是：每个文件只有一个权威用途、每类资产有唯一落点、数据安全默认关闭。

## 开工前确认

只问影响结构的四件事：

1. **客户与平台**：客户名、agent 平台（如某企业智能体平台）、交付形态（项目内对话挂专家/技能，还是独立应用）。
2. **已有约定**：仓库已有 `AGENTS.md` / `CLAUDE.md` 时**先读**——它是结构之母，按其文档体系落地；发现路径自相矛盾（如 `docs/TODO.md` 与 `docs/进度追踪.md` 并存）先统一，再建目录。
3. **现有资料**：需求文档、数据样本、原型。原始数据只登记存放位置，不入库。
4. **交付动作**：是否做首次提交；初始化技能沉淀到个人技能库还是项目 `.qoder/skills/`。

## 目录骨架（按需裁剪）

```
<repo>/
├── AGENTS.md          # 工作约定（已有则修订，不重写）
├── README.md          # 仓库说明、目录契约、原则、数据安全
├── CONTEXT.md         # 术语表，新会话先读
├── docs/
│   ├── 进度追踪.md     # 唯一进度权威（只记状态与待办）
│   ├── 用户需求整理.md  # 会议需求总账：客户原话 + 导航
│   └── 业务落地方案/
│       └── 需求N-主题/  # 需求.md + 方案.md + 原始材料/
├── agents/            # 平台专属专家/技能定义
├── evals/             # 评测集与真实数据回放
├── prototype/         # 对客原型
├── scripts/           # 数据处理/对账/复算脚本
└── data/
    ├── raw/           # 原始数据（禁止全量读取，不入库）
    └── output/        # 脚本产物（不入库）
```

没有对应交付物就不建目录（例如平台无独立应用，就不建 app/）；空目录用 `.gitkeep` 占位。

## 必建文件

### README.md

固定五块：一句话定位（客户 + 平台 + 交付范围）／目录表（每个目录「放什么、不放什么」）／落地原则摘要／数据安全红线／新会话阅读顺序（CONTEXT → 进度追踪 → AGENTS）。

目录表是契约：新增目录必须同步更新。

### CONTEXT.md

只登记**已确认**的词汇：客户、平台、产品入口、角色、交付形态、需求编号规则。格式 `术语 | 释义 | 备注`。不确定的不写。

### docs/进度追踪.md

唯一进度权威，三节：需求确认进度 / 方案实施进度 / 待办。待办分两阶段：

- 阶段一 = 需求确认收尾：按对接方分组（IT / 客户 / 领导 / 内部），每条含事项、话术或附件位置、加入日期。
- 阶段二 = 实施期规划：需求确认后的实施与验收，现阶段不动工。

完成项移入「已完成」并保留日期与解决方式，不删行。

### docs/用户需求整理.md

**会议需求总账**。记录客户在会议、邮件、IM 中的原始诉求（原话、来源、日期），只做需求入口与导航：整理后的口径与方案指向需求目录，不在此复述。未立项的诉求同样登记、需求目录列留空，立项后补链接，不删除原话。

### docs/业务落地方案/需求N-主题/

一个需求一个目录，目录内即该需求的全部真源：

- `需求.md`：背景、范围、口径、验收、澄清记录（澄清过程并入本文，不另立文件）。
- `方案.md`：流程、规则、边界、实施步骤。
- `原始材料/`：客户原始材料（会议纪要、截图、邮件、样本）；大批量数据仍放 `data/raw/` 且不入库。

不按版本另存文件（`-v2`、`-终版`、`-副本`），版本交给 git；对外交付版从真源派生导出。

### .gitignore

至少忽略：`data/raw/*`、`data/output/*`（用 `!.gitkeep` 保留目录）、`__pycache__/`、`.venv/`、`.env*`、密钥文件、`.DS_Store`、工具临时目录。

## 单一真源（需求文档结构的硬约束）

1. 同一需求的需求正文只存在于 `需求.md`，方案正文只存在于 `方案.md`；其他文档只做导航、摘要或状态，不复述正文。
2. 一个需求一个目录，不在文件名上管版本（禁止 `-v2`、`-终版`、`-副本`、`-日期` 另存），版本交给 git 历史。
3. 会议总账只记客户原话与链接；进度追踪只记状态与待办；两者都不写整理后的结论。
4. 澄清记录并入 `需求.md`；证据件放该需求 `原始材料/` 或就近存放并链接。
5. 对外交付版从真源派生，不手工维护第二份正文。

## 落地原则

写进 README 摘要即可，完整执行细则留在 AGENTS.md，避免双源：

1. **落地即体检**：主动排查客户流程中已有的数据与流程坏点，坏点不修进自动化。
2. **可验证**：结论可复算（脚本 + 明细落盘），验收用真实数据回放，AI 产出标来源与置信度。
3. **可观测**：原始数据保留，结果带溯源，识别不了的显式标注。
4. **流程内生一致**：优先复用系统既有机制，不新建需要人持续维护的对照/映射资产。

## 验收清单

- [ ] AGENTS.md 已读；仓库名、客户名、引用的文档路径无旧仓遗留（复制来的 AGENTS.md 必查这三项）
- [ ] AGENTS 只留通用约定 + 指针（细节进 docs 并留指针），无跨文件重复正文
- [ ] README 目录表与真实目录逐项一致
- [ ] 进度、需求、术语各只有一个权威文件，无重复正文
- [ ] 每个需求只有一份 `需求.md` 和一份 `方案.md`，目录内无 `-v2`/`-终版`/副本
- [ ] 会议总账只有原话与链接，进度追踪只有状态，均未复述正文
- [ ] `git status` 人工过一遍：无数据、产物、密钥进暂存区
- [ ] 空目录有 `.gitkeep`
- [ ] 首次提交完成
- [ ] 新会话按 README 的阅读顺序能独立接手

## 反模式

- 一个需求拆成需求文档、澄清文档、方案 v2 等多份文件；会议总账里写整理后的结论。
- 先建一堆目录再补用途；为「以后可能用」提前建空结构。
- README 与 AGENTS 各写一份原则，后续两边不同步。
- 把客户原始数据、脚本产物、账号密钥提交入库。
- 未确认交付形态就建应用目录（项目内对话类平台是对话 + 挂专家/技能）。
- 用演示样例充当验收证据；进度追踪只加不清、完成项直接删行。

## 经验来源

2026-10-23 一次客户交付仓初始化：从相邻项目沿用的 AGENTS.md 带入了旧仓库名、`docs/TODO.md` 与 `docs/进度追踪.md` 两套路径、指向不存在文件的引用——说明**结构规划始于逐行核对已有约定**，而不是另起一套。同日针对「文档太散太多」定稿单一真源结构：会议需求总账做入口，需求按目录归拢，需求/方案各一份正文。本技能的目录骨架、权威文档与验收清单由此沉淀。
