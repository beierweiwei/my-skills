# 项目工作约定

## 文档职责

- `README.md`：一句话定位、目录表（每个目录放什么、不放什么）、落地原则摘要、数据安全红线、新会话阅读顺序（CONTEXT → 进度追踪 → AGENTS）。目录表是契约，新增目录必须同步更新。
- `CONTEXT.md`：只登记已确认的词汇（主体、平台、产品入口、角色、交付形态、编号规则），格式 `术语 | 释义 | 备注`；不确定的不写。
- `docs/用户需求整理.md`：会议需求总账，只记原始诉求（原话、来源、日期）与链接；整理后的口径与方案指向需求目录，不复述。未立项诉求同样登记，立项后补链接。
- `docs/进度追踪.md`：唯一进度权威，三节：需求确认进度／方案实施进度／待办。完成项移入「已完成」并保留日期与解决方式，不删行。
- `docs/需求N-主题/`：一个需求一个目录，该需求的全部真源：`需求.md`（背景、范围、口径、验收、澄清记录）、`方案.md`（流程、规则、边界、实施步骤）、`原始材料/`（会议纪要、截图、邮件、样本）。

## 单一真源

1. 同一内容只保留一份权威正文；其他文档只做导航、摘要或状态，不复述正文。
2. 一个需求一个目录，不按文件名管版本（禁止 `-v2`、`-终版`、`-副本`、`-日期`），版本交给 git 历史。
3. 会议总账只记原话与链接；进度追踪只记状态与待办；两者都不写整理后的结论。
4. 澄清记录并入 `需求.md`；证据件放该需求的 `原始材料/` 或就近存放并链接。
5. 对外交付版从真源派生，不手工维护第二份正文。

## 数据安全

- `data/raw/`：原始数据，禁止全量读取，不入库。
- `data/output/`：脚本产物，不入库。
- 密钥、账号配置、`.env*` 不入库。
- 空目录用 `.gitkeep` 占位，`.gitignore` 用 `!.gitkeep` 保留目录。
- 提交前人工过一遍 `git status`，确认暂存区无数据、产物、密钥。

## 落地原则

1. **落地即体检**：主动排查流程中已有的数据与流程坏点，坏点不修进自动化。
2. **可验证**：结论可复算（脚本 + 明细落盘），验收用真实数据回放，AI 产出标来源与置信度。
3. **可观测**：原始数据保留，结果带溯源，识别不了的显式标注。
4. **流程内生一致**：优先复用系统既有机制，不新建需要人持续维护的对照/映射资产。
5. **验证资产跟随产品**：首个可跑版本出现后，调用 `create-verification-skill` 生成项目验证技能与 feature map；后续用 `maintain-verification-skill` 周期审计，防验证资产漂移。

## 反模式

- 一个需求拆成需求文档、澄清文档、方案 v2 等多份文件；会议总账里写整理后的结论。
- 先建一堆目录再补用途；为「以后可能用」提前建空结构。
- README 与 AGENTS 各写一份完整原则，后续两边不同步。
- 把原始数据、脚本产物、账号密钥提交入库。
- 未确认交付形态就建应用目录。
- 用演示样例充当验收证据；进度追踪只加不清、完成项直接删行。
